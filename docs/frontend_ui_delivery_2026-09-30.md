# 桌宠与工作台 UI 工程交付

## 工作区创建失败修复

运行日志显示旧会话请求 `POST /pet/session-workspace` 返回 422。首次修订放宽了会话 ID 限制：普通 ID 仍直接用作目录名，其他 ID 则通过 SHA-256 映射到固定、安全的子目录。后续根据用户提供的 `Field required` 错误继续复现，确认这不是 Java 桌宠的主要故障：Java 默认 HTTP/2 向本地 Uvicorn 发起请求时，同一 JSON 请求返回 422，响应指出整个请求体缺失；强制 HTTP/1.1 后返回 200。浏览器工作台没有这个错误。

验证：`tests/test_desktop_pet.py` 共 7 项通过；Windows Node 语法检查通过；本机 Windows 前端服务已重启，`/pet/manifest` 返回 200，真实 HTTP 请求使用 `legacy:workspace-probe` 这样的旧格式 ID 创建工作区成功。诊断产生的空目录已清理。当前打开的面板重新打开或点击“刷新”即可重试创建。

Java 右键面板现在通过 `PetChatBridge.createSessionWorkspace` 使用 Java HttpClient 的 HTTP/1.1，向同一个 `POST /pet/session-workspace` 发送相同的 `{"session_id": ...}` JSON。桥接在 WebView 页面载入后安装；安装完成时会重试页面初始化期间失败的工作区创建。发消息流程会先创建并绑定工作区，此前 422 会使 Agent 请求根本没有发出；该传输修复解除这一前置阻断。浏览器继续使用同一接口的 `fetch`。

桌宠小人的位置由 Win32 提供物理像素，而 JavaFX 小窗口使用按屏幕缩放的逻辑坐标。小窗口跟随改为按位置差值和 `Screen.getOutputScaleX/Y()` 移动，在 200% DPI 下，桌宠移动 100 个物理像素时小窗口移动 50 个 JavaFX 坐标单位；直接拖动小窗口仍按鼠标屏幕坐标处理。真实鼠标手感仍需在 Windows 图形桌面确认。

## 发消息无响应：两处独立故障与实测

Java 右键面板的消息发送会先创建并绑定会话工作区，再调用 `/agent/turn/stream` 或 `/agent/turn`。旧版 WebView 创建工作区时收到 `HTTP 422: Field required`，故 Agent 根本没有收到那条消息。浏览器工作台使用同一 `POST /pet/session-workspace` JSON 接口，但其浏览器请求正常。Java 面板现通过原有 `petBridge` 以 HTTP/1.1 调用相同接口，并在桥接安装后重试页面初始化期间失败的创建请求。对一条失败时创建的空会话进行实测，前端创建工作区与后端 `PUT /sessions/{id}/workspace` 均成功。

继续用该会话直接调用后端发现第二个故障：后端虽然健康，原默认模型 `deepseek-v4-flash` 的两次调用均返回上游 `model_not_found`（HTTP 503）。已配置的模型目录只列出 `deepseek-flash` 与 `deepseek-v4-pro`。本地忽略文件 `config/local.toml` 的默认模型已改为 `deepseek-flash`，并重启后端。请求级覆盖验证和重启后的默认模型验证均返回 Agent 回答，两次模型审计状态均为 `completed:deepseek-flash`。 默认流式接口也返回 HTTP 200，收到 86 个 SSE 事件，其中包含 `final_answer` 与 `run_completed`，没有 `run_failed`。当前 Java 桌宠也已重启为修复版；Java 编译成功，前端静态页与后端健康接口可访问。真实面板点击发送和鼠标拖动手感仍需在 Windows 图形界面确认。

## 首条消息仍无响应：会话响应结构修复

用户再次报告 Java 面板显示“发送失败：cannot create backend session”，网页端没有该错误却没有回复。服务日志显示两端都执行了旧会话工作区绑定（404）和 `POST /sessions`（200），但没有继续第二次绑定或 Agent 请求。后端 `POST /sessions` 的真实响应是 `{"session":{"session_id":"..."},"messages":[]}`；前端错误地只读取顶层 `session_id`，因此把成功创建误判为失败。浏览器与 Java 桥接共用的 `chat.js` 现同时兼容嵌套 `session.session_id` 和旧的顶层格式。

切换为后端会话 ID 时，前端现在同步更新等待回复的会话 ID，并重新取得当前会话对象，确保流式回复显示在正在查看的会话。`chat.html` 的脚本版本已更新，Java 桌宠已重启加载新脚本。

隔离 Edge 实测全新会话首次发送“你好”：工作区绑定经历 404 → `POST /sessions` 200 → 新 ID 工作区绑定 200 → `/agent/turn/stream` 200，页面状态为“本轮完成”，回答可见，脚本错误为空。模拟 Java 桥接同步方法的独立实测也完成同样的 404 → 新建 → 绑定 → Agent 200 路径，回答显示在当前会话。JavaFX 真实鼠标点击发送仍需用户界面验收。

## 技术实现

- 工作区默认位置：Windows“文档”已配置的实际位置下的 `Local Knowledge Agent/Workspaces/<session_id>`（常见路径是 `%USERPROFILE%/Documents/...`）。可用环境变量 `LKA_SESSION_WORKSPACE_BASE` 指定其他父目录；用户未选择其他位置时，每个新会话使用自己的子目录。
- 前端服务新增 `POST /pet/session-workspace`，仅接受本机请求和安全的会话 ID。默认在文档目录下创建子目录；设置绝对 `base_path` 后，新会话改在该父目录下创建。实际工具工作区仍通过 LKA 后端既有 `PUT /sessions/{session_id}/workspace` 校验和绑定。
- 快速面板与工作台使用同一个聊天页，通过 `?mode=quick` 和 `?mode=work` 控制布局。浏览器窗口共享同源 localStorage；另一个窗口更新会话时会同步刷新。
- Qt 宿主按目标模式调整窗口尺寸，pywebview 宿主默认打开快速面板，JavaFX 宿主增加工作台入口。
- 视觉采用冷纸白、深海蓝、青绿和少量暖金；选项和下拉框与输入框使用同一套边界、焦点和尺寸规则。

## 安全审查、最终回复与 Java Enter 键修复

2026-09-30 的实际运行 `agent_run_c3e2198339f5` 中，后端完成了回答（`final_answer` 事件携带 1313 字回复，会话消息也已保存）。`mail.sync` 的审查模式为 `skip`，`safety_review_required` 后 56 毫秒由 `system.skip` 自动批准，审批队列没有待处理项。旧前端却把每个 `safety_review_required` 都显示为“等待安全审查确认”，而“安全审查”下拉框只保存本地设置、从未传入浏览器或 Java 桥接请求。真正的人工待审信息原先也只挤在对话区的一条小横幅内。

现在只有 `manual` 且 `pending` 的审查显示“等待确认”。人工队列以固定居中的对话框呈现工具、风险、理由、可能影响、涉及字段以及允许/拒绝按钮；队列仍由后端 `GET /agent/safety-reviews` 提供，不向前端暴露原始工具输入。前端的安全模式随 `/agent/turn`、`/agent/turn/stream` 以及 Java 桥接传递。后端接受可选的 `safety_review_mode`，取请求与本地配置中更严格的值，防止前端选“自动通过”绕过后端策略。此字段已写入后端 API 契约。

回复不可见的前端风险有两处：页面初始化的异步会话同步可能在正在发送时切换当前会话或覆盖本地消息；流式完成后过度依赖暂存在 WebView 的事件答案。现在同步过程保护发送中的会话，并在 `run_completed` 后从后端会话详情取回正式消息，作为 Java 桥接和浏览器流的统一恢复路径；重新连接已保存的运行也会恢复正式回复。`final_answer` 同时兼容事件中的完整 `message` 字段。JavaFX WebView 增加原生 Enter 处理：输入框聚焦时 Enter 发送，Shift+Enter 留给换行；网页输入框另加默认换行拦截，避免 JavaFX 在提交后插入换行。

## 输入法位置与忙碌期间草稿输入

Java 桌宠右键窗口原先把输入框放在 JavaFX WebView 的网页内。用户反馈 Windows 输入法候选框有时出现在桌宠形象旁边；从前端结构看，候选框位置由 WebView 宿主报告，网页 CSS 无法可靠修正其屏幕坐标。现在 Java 快速窗口使用 JavaFX 原生 `TextArea` 和原生发送按钮，网页输入框仅在 Java 宿主中隐藏。原生输入框直接使用所在窗口的文本输入定位；浏览器工作台继续使用网页输入框。原生 Enter 发送、Shift+Enter 换行，输入法正在组合候选词时不会将 Enter 当作发送。

旧 `setComposerDisabled` 同时禁用了文本框和发送按钮。现在处理期间只禁用发送，文本框保持可编辑；第二条草稿不会因按 Enter 或当前轮结束而清空。Java 宿主通过 `PetChatBridge.setComposerBusy` 同步发送按钮状态，并在用户切换会话或选欢迎页建议时把焦点或草稿交给原生输入框。

验证：Windows Node 语法检查与 Java `compileJava --offline` 通过。隔离浏览器在模拟 Agent 持续运行时观察到发送按钮禁用、输入框保持启用、Java 原生桥接状态同步；下一条草稿在忙碌时不能被误发，在当前轮完成后仍完整保留，未出现脚本异常。输入法候选框的最终位置需要在用户所用 Windows 输入法和屏幕缩放组合下做桌面实测。

## Markdown 回复渲染

真理的回复此前直接写入 `textContent`，历史消息、流式输出与旧桌宠面板都显示原始 `##`、`**`、代码围栏等 Markdown 标记。现在三个入口共用本地打包的 `markdown-it 15.0.2` 浏览器构建与 `markdown.js`，离线可用。支持标题、强调、列表、引用、表格、代码块、行内代码和链接；流式输出按约 80 毫秒合并渲染，最终答案立即刷新，历史会话重新打开时也使用相同排版。宽表格和代码块可横向滚动，快速窗口与工作台共享 `markdown.css` 的排版规则。

Agent 输出按不可信内容处理：关闭原始 HTML，只允许明确的 `http(s)` 与 `mailto` Markdown 链接；危险协议不会生成链接，远程图片显示为可点击的图片链接而不会自动加载。Java 桌宠点击外链时由桥接调用系统浏览器，并再次验证 URL 协议。解析器固定版本及其 MIT 许可证随静态资源交付。

验证：Windows Edge 中检查标题、粗体、列表、表格、代码、引用与外链均生成对应 DOM；`<script>` 保持纯文本，`javascript:` 不生成链接，图片不自动加载。模拟流式 Agent 完成事件后，正式回复显示标题和列表而非原始符号，页面无脚本异常。430×680 快速窗口截图确认表格和代码块未撑破布局。Windows JavaFX WebView 独立运行同一离线解析器，标题、列表和代码渲染探针通过（`JAVAFX_MARKDOWN_READY=true`）；Java `compileJava --offline` 与 Node 语法检查通过。

## 会话删除与恢复

原因：侧栏“删除”此前只从 `chat.js` 的内存数组和浏览器 `localStorage` 中移除会话；页面启动后 `syncSessionsFromBackend()` 调用 `GET /sessions`，将仍保存在后端 SQLite 中的同一会话重新导入，因此重启后会再次出现。

现在后端 `DELETE /sessions/{id}` 只将状态标记为 `deleted`，正常列表与详情不再显示；`GET /sessions/deleted` 和 `POST /sessions/{id}/restore` 提供回收列表与恢复。前端只有在后端删除成功（或确认会话尚未写入后端的 404）后才更新本地列表；失败时保留会话并显示错误。Java 桌宠的删除与恢复通过原有 HTTP/1.1 桥接。侧栏“已删除”可查看、搜索、恢复会话。未发送过消息的本地草稿没有后端行，因此保留本地快照以供恢复。跨窗口本地存储与启动时后端同步使用删除标记避免旧请求重新带回会话。

工作区文件、历史消息与运行审计不会被物理删除。没有实现过期清理或定时清理。旧版前端删除只留下“当前列表缺少该会话”的状态，无法从后端判定哪些旧会话曾被点击删除；这些已经重新出现的会话需要在新版中再删除一次。

验证：后端 `tests/test_sessions.py` 共 8 项通过；Windows Java `compileJava --offline` 通过，前端脚本语法与 `git diff --check` 通过。隔离 Edge 和临时后端完成删除→页面重载→“已删除”中恢复，恢复后原消息仍在且无脚本异常；未发送草稿也完成删除→恢复，工作区路径保持一致。临时后端进程重启后，会话仍在已删除列表中、普通列表不显示，恢复后消息仍保留。

补充跨入口验证：使用另一进程直接在临时后端删除会话，再刷新隔离浏览器，旧本地记录会从普通列表移到“已删除”；从另一进程恢复并再次刷新后，会话回到普通列表，本地删除标记清除。测试无脚本异常，隔离配置及临时工作区已清理。
